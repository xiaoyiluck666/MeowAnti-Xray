# 1.5.0 Dual-loader Pressure Matrix

Status: complete

## Purpose

Measure Fabric and NeoForge async rewrite behavior under the same Minecraft 26.2 workload before changing scheduling, allocation, or the default queue size.

## Controlled Method

- Mainline commit: `ced5013` (`1.5.0` release preparation).
- Java: `25.0.2`.
- Minecraft: `26.2`, protocol `776`.
- Eight fresh network fake players per sample.
- 90-second spectator route with RCON teleports, 192-block steps, Y=180.
- Fresh server process for every sample.
- Queue screening: `0`, `16`, `32`, `64`.
- Queue `16` and queue `32` repeated three times per loader.
- Raw structured samples are stored under ignored `build/pressure-results/`.

The collector records the environment, config SHA256, active queue, runner result, and final `/antixray status`, `/antixray config`, and `/antixray profile`.

All samples had 8/8 clients in play, zero runner errors, non-zero rewrite activity, and a confirmed active queue. Queue `64` produced the highest single-run throughput, but Fabric ended that sample with 37 in-flight tasks. Queue `32` also reached in-flight 22 in one NeoForge repeat. These are pressure signals, not packet-loss reports, but they disqualify both values from becoming the default based on this matrix.

## Decision

- Keep the default `async-queue-size: 16`.
- Keep `32` and `64` as documented manual tuning options for servers with sufficient memory.
- Use `/antixray profile` after changing the queue and confirm that `inFlight` returns to zero between bursts.
- No scheduling or snapshot-allocation code change is justified by this matrix.

## Evidence Limits

The collector records runtime rewrite pressure but does not automatically capture spark TPS/MSPT or heap snapshots. Since the release keeps the existing default and introduces no scheduling change, this is a release evidence gap rather than a reason to raise the queue. Future tuning work should add spark health and heap capture before considering a default change.
